# Intake, conflicts, closure and reopening

Use this when opening/linking a matter, doing a requested conflict review or
preparing closure/reopening. It adds research/checklists, not new register fields
or legal clearance. Follow the installed tracker for all actual operations.

## Before creation

Establish proposed client, engagement/subject, roles, entities/principals,
opposing/related parties, meaningful name variants, contacts, actual opening
date when known, folder candidate, known commitments and date inputs. An early
email is not necessarily the engagement date. Resolve whether an existing file
is the same matter, a separate engagement or a closed file needing reopening.
Do not choose from competing candidates by resemblance.

Search open and closed register fields using the declared candidate-screening
interface, by meaningful names/variants and roles. Classify hits as possible
duplicate, current/former-client adversity, related/affiliate, repeat opposing
party or unresolved name match. A shared opposing party is not itself a conflict.
Re-screen material parties discovered during intake or evidence review.

A fuller requested search may include available authorized folder-name sources
and bounded mail through an actually present approved read/search route. State
terms, sources, time bounds, caps and unopened leads. The bundled single-matter
intake is not an all-time cross-matter conflict search; do not relabel its query
or substitute another account. Unavailable sources remain disclosed gaps.

Report "no located hit in the sources searched", never professional clearance.
Put adverse-interest/confidential-knowledge decisions to the lawyer, using the
minimum other-client metadata required. Do not open another client's records or
copy privileged details merely because a party matched.

## Proposal and completion

Present supported canonical fields and their sources, matched existing folder,
intake events/contacts, next action and unconfirmed legal inputs. Also list exact
requested downstream artifacts, Calendar effects or reciprocal related-file
records separately. Do not create or invent an unverified folder.

The current schema has no dedicated conflict-clearance, identity-verification,
engagement-date, related-matter or practice-manager completion fields. Record
these as lawyer decisions/open questions in the response or an expressly
approved ordinary matter record; do not issue an unsupported tracker assignment.
Keep conflict/identity completion pending in that prose until the lawyer
confirms the actual step. These notes are not a compliance certification.

Use one exact tracker preview/approved commit at a time, read back and reconcile
uncertain outcomes under its existing contract. Never restart creation after a
later branch fails. Perform only approved downstream operations that actually
exist. Report register, artifact, Calendar and unsupported/manual branches
separately, with precise partial results and remaining decisions.

## Closing or reopening

Before proposing status change, read current surviving obligations, dates,
undertakings, unresolved risks, next actions and relevant recent evidence.
Identify what remains after closure and what reopening is intended to resume.
Neither age nor inactivity proves work finished.

Show the status proposal plus exact proposed memory/next-action/Calendar effects.
Deleting a Calendar event or clearing a protective date requires its own
explicit bounded approval. Change status only through the installed tracker,
verify it, then perform supported separately approved follow-through. A failed
downstream operation never silently reverses or conceals the tracker result.
Closed matters remain read-only until an approved reopening succeeds.
